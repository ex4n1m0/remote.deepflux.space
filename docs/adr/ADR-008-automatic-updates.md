# ADR-008: Automatic updates — a manifest on the landing, the app does the rest

- Status: Accepted (0.9.0, 2026-10-28)
- Deciders: main session (integrator) on the user's 2026-10-28 request
  ("let's add a automatic update engine"), user's standing preferences
  (one installer, simplicity over separation —
  `memory/user-working-style.md`), reviewed by the code-review, UX, and
  release seats before release.
- Sources: `apps/desktop/src-tauri/src/updater.rs` (engine),
  `dl.rs` (`start_in_dir`), `commands.rs` (update commands),
  `store.rs` (`auto_update`), `apps/desktop/src/components/UpdateBanner.tsx`,
  `scripts/publish-landing.sh` (manifest generation),
  ADR-006 distribution addendum (one family build IS the public
  download).

## Context

Every release so far shipped as a manually-copied installer on the
landing page, and the landing's version strings were hand-edited each
time — the known "stale website" trap the release-reviewer seat exists
to catch (it bit 0.5.x). Machines in the field keep whatever version
they installed; family members do not watch remote.deepflux.space. With
the product in daily family use, the next security or UX fix needs a way
to reach installed copies without "reinstall from the website"
instructions.

Tauri's official updater plugin was evaluated and rejected for this
codebase: it wants updater artifacts (MSI/signing infrastructure) we do
not have, drags a new dependency tree, and its trust model adds nothing
we do not already get from HTTPS-to-our-domain — the builds are
unsigned either way (landing fineprint; code signing is a post-MVP
item).

## Decision

1. **`latest.json` on the landing is the update contract** —
   `{product, version, url, sha256_hex, size_bytes, notes,
   published_at}`, generated by `scripts/publish-landing.sh` in the same
   step that stages the installer and patches the landing page's
   version/size strings (the staleness trap dies with it). The manifest
   is committed; the exe is not (`.gitignore` as before).
2. **The client engine** (`updater.rs`, app crate — no new external
   dependencies): fetch the manifest at startup (+20 s) and every 24 h,
   or on demand (Help → Check for updates). The settings toggle
   `auto_update` (default ON) silences only the scheduled checks.
   Validation is strict: product id match, dotted-numeric version,
   installer URL HTTPS **and same-host as the manifest** (origin pin, no
   suffix matching), 64-hex SHA-256, size within the download cap. A
   malformed manifest is an error, never a "try anyway".
3. **Update is two deliberate presses.** "Update now" downloads via the
   existing hardened segmented engine (`dl.rs`) into
   `<appdata>/updates/`, resumable, then verifies size + SHA-256 against
   the manifest — an unverified installer never runs; a mismatch deletes
   the staged file. "Restart & update" runs the NSIS installer silently
   (`/S`; currentUser mode = no UAC), quits the app (engine shutdown
   first — the peer hears a clean disconnect), and relaunches it via a
   detached `cmd` wrapper that waits out the install. Install refuses
   while any session machinery is live — connected, consent-prompted, or
   mid-handshake, either role (the states outside `Idle / Registering /
   Online / Disconnected`) — the app dying under an active remote
   session is exactly the failure the consent philosophy exists to
   prevent. The staged installer is re-verified at install time (it may
   have sat on disk for days).
4. **Trust model, stated plainly:** identical to the manual download —
   HTTPS to remote.deepflux.space plus a SHA-256 from the same manifest.
   That protects against transport/CDN corruption and truncation, NOT
   against a compromised origin (an attacker who controls the site
   controls both manifest and exe today, with or without the updater).
   The upgrade path is code signing + signature verification, to be
   revisited when a certificate exists. No version downgrade: a
   manifest version ≤ installed is "up to date".
5. **Bootstrapping:** 0.9.0 is the first build carrying the engine;
   everything before it updates manually one last time. The updater
   ships enabled by default, quiet by default (no update → no UI), and
   "Not now" silences a version until restart — except for an explicit
   Help → Check for updates, which re-offers and always answers (a
   "checking" line, then the banner or an up-to-date notice that
   self-dismisses). A transient check failure never retracts a standing
   offer, and clearing an error banner never declines the update
   ("Try again" re-runs the failed stage).

## Consequences

- New IPC surface (all metadata, walked by the ipc-surface test):
  `update_state/check/download/install/dismiss` + `update://state`
  events. Payload field names avoid the byte/secret forbidden-substring
  list by construction (progress is a percent + human size string).
- The `dl` engine gains `start_in_dir` (destination directory
  parameter); the Downloads-folder default behavior is unchanged.
- Publishing now REQUIRES the script (or manual equivalence): a
  hand-copied exe without a matching `latest.json` means installed
  clients stay on the old version with no signal — the failure is
  silent, so the release checklist names the script explicitly.
- Installers remain unsigned; SmartScreen still warns on first run of
  the downloaded installer. The wrapper runs it anyway — that is the
  user's explicit press on "Restart & update".
- Windows-only by construction (NSIS + cmd wrapper + creation flags);
  harmless no-ops elsewhere (`detached_flags` stub), like the rest of
  the product (Windows-first).
- Rejected alternative (recorded): `tauri-plugin-updater` — needs
  updater artifacts/signing infra we lack; revisit together with code
  signing.
